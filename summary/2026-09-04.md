### Q1. CORS(Cross-Origin Resource Sharing)란 무엇이며, 발생 원인과 해결 방법(서버 헤더 설정, 프록시 등)을 설명해주세요.

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/Esoolgnah/Frontend-Interview-Questions/blob/main/Notes/important-3/how-to-handle-cors-error.md)

**모범 답변:**
CORS는 브라우저의 동일 출처 정책(Same-Origin Policy) 때문에 다른 출처(도메인/포트/프로토콜)의 리소스 요청이 기본적으로 차단될 때, 서버가 특정 출처의 접근을 허용한다고 브라우저에 알려주는 보안 메커니즘입니다. GET 등 단순 요청은 서버 응답에 `Access-Control-Allow-Origin` 헤더가 있으면 허용되고, PUT/DELETE 같은 비단순 요청은 브라우저가 먼저 `OPTIONS` 메서드로 Preflight 요청을 보내 허용 여부를 확인합니다. 해결 방법으로는 서버 측에서 CORS 허용 헤더를 설정하거나, 개발 환경에서는 프록시 서버를 두어 브라우저가 동일 출처로 인식하게 만드는 방식이 흔히 쓰입니다.

### Q2. 쿠키(Cookie)와 세션(Session)의 차이점은 무엇인가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/gyoogle/tech-interview-for-developer/blob/master/Web/Cookie%20%26%20Session.md)

**모범 답변:**
쿠키는 클라이언트(브라우저)에 텍스트 형태로 저장되지만, 세션은 서버에 객체 형태로 저장되고 클라이언트는 세션 ID만 쿠키로 전달받습니다. 쿠키는 만료 시간을 직접 설정할 수 있어 브라우저 종료 후에도 유지될 수 있지만, 세션은 보통 브라우저 종료나 서버 설정 시간에 따라 만료됩니다. 세션은 서버 리소스를 사용하므로 트래픽이 많으면 서버 부하가 커지고, 쿠키는 클라이언트에 노출되므로 민감 정보 저장에 주의해야 합니다. 로그인 유지 같은 인증 정보는 보통 세션 ID(또는 토큰)를 담은 쿠키로 관리합니다.

### Q3. HTTP 상태 코드(2xx, 3xx, 4xx, 5xx)는 각각 어떤 상황을 의미하나요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/gyoogle/tech-interview-for-developer/blob/master/Web/HTTP%20status%20code.md)

**모범 답변:**
1xx는 정보성 응답, 2xx는 성공(200 OK, 201 Created 등), 3xx는 리다이렉션(301 영구 이동, 304 Not Modified 등)을 의미합니다. 4xx는 클라이언트 오류로 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found가 대표적이고, 5xx는 서버 오류로 500 Internal Server Error, 503 Service Unavailable 등이 있습니다. 프론트엔드에서는 이 상태 코드를 기반으로 에러 핸들링, 재시도, 리다이렉트 로직을 분기하는 데 활용합니다.

### Q4. HTTP의 Cache-Control 헤더와 브라우저 캐싱 전략에 대해 설명해주세요.

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/leegwae/getting-started/blob/main/computer-network.md)

**모범 답변:**
`Cache-Control` 헤더는 브라우저와 CDN 같은 중간 서버에게 리소스를 얼마나, 어떻게 캐싱할지 지시하는 HTTP 헤더입니다. `no-cache`는 캐시를 쓰기 전 서버에 유효성 재검증을 요구하고, `no-store`는 아예 캐싱하지 않으며, `max-age=N`은 N초 동안 캐시를 그대로 사용하게 합니다. 실무에서는 JS/CSS/이미지 같은 정적 자산은 파일명에 해시를 붙여 `max-age`를 길게 주고, HTML이나 API 응답은 짧게 주거나 `no-cache`로 최신 데이터를 보장하는 전략을 흔히 사용합니다. 이를 통해 불필요한 네트워크 요청을 줄여 로딩 속도와 서버 부하를 개선할 수 있습니다.

### Q5. REST API란 무엇이며, RESTful하다는 것은 어떤 의미인가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/gyoogle/tech-interview-for-developer/blob/master/Web/%5BWeb%5D%20REST%20API.md)

**모범 답변:**
REST(Representational State Transfer)는 자원을 URI로 표현하고, 자원에 대한 행위를 HTTP 메서드(GET/POST/PUT/PATCH/DELETE)로 표현하는 아키텍처 스타일입니다. RESTful하다는 것은 자원 중심의 URI 설계, 상태를 갖지 않는(stateless) 통신, 명확한 HTTP 메서드와 상태 코드 사용 같은 원칙을 지킨다는 의미입니다. 예를 들어 `GET /users/1`은 조회, `POST /users`는 생성, `PUT /users/1`은 수정, `DELETE /users/1`은 삭제를 나타냅니다. 이 설계 원칙을 이해하면 서버와의 통신 구조를 예측하고 효율적으로 클라이언트 코드를 작성할 수 있습니다.
