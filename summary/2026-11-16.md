### Q1. 브라우저 주소창에 URL(www.google.com)을 입력하면 어떤 일이 일어나나요?

> **importance_score**: 4/5 | **빈출**: high | **출처**: [링크](https://www.youngju.dev/blog/culture/2026-03-24-how-browsers-work-rendering-pipeline-guide)

**모범 답변:**
브라우저 캐시 → OS/리졸버 순으로 DNS 조회해 도메인을 IP로 바꿉니다.
해당 IP와 TCP 연결(3-way handshake)을 맺고, HTTPS라면 TLS 핸드셰이크로 암호화 채널을 만듭니다.
HTTP 요청을 보내고 받은 HTML을 파싱해 DOM/CSSOM → 렌더 트리 → Layout → Paint → Composite 순으로 화면에 그립니다.
파싱 중 만난 CSS·JS·이미지 같은 하위 리소스도 추가로 요청하며, 실무에서는 각 단계를 DNS prefetch·preconnect·CDN 등으로 최적화합니다.

### Q2. 브라우저 렌더링 과정(Critical Rendering Path)을 설명해 주세요.

> **importance_score**: 4/5 | **빈출**: high | **출처**: [링크](https://www.it-server-room.com/2025/07/02/)

**모범 답변:**
① HTML을 파싱해 DOM, CSS를 파싱해 CSSOM을 만듭니다.
② 둘을 합쳐 화면에 보이는 노드만 담은 렌더 트리를 구성합니다(`display: none` 요소는 제외).
③ Layout에서 각 노드의 크기·위치를 계산하고, ④ Paint에서 픽셀로 그린 뒤, ⑤ Composite에서 레이어를 합성해 화면에 표시합니다.
CSS는 렌더 블로킹, 동기 JS는 파서 블로킹 리소스이므로 Critical CSS 인라인·스크립트 지연 로딩으로 첫 화면을 앞당깁니다.

### Q3. 리플로우(Reflow)와 리페인트(Repaint)의 차이와 각각 언제 발생하는지 설명해 주세요.

> **importance_score**: 4/5 | **빈출**: high | **출처**: [링크](https://www.it-server-room.com/2025/07/02/)

**모범 답변:**
리플로우는 요소의 크기·위치가 바뀌어 Layout을 다시 계산하는 것이고, 리페인트는 레이아웃 변화 없이 색·배경·그림자 등 시각 속성만 다시 그리는 것입니다.
width/height/margin/font-size 변경, DOM 추가·삭제, 창 크기 변경, `offsetHeight` 같은 레이아웃 값 읽기 시 리플로우가 발생합니다.
`color`, `background-color`, `visibility` 변경은 리페인트만 일으킵니다.
리플로우는 리페인트를 항상 동반하므로 비용이 더 큽니다.

### Q4. 리플로우·리페인트를 줄이는 방법은? (transform/opacity, 합성(Composite) 레이어, GPU 가속)

> **importance_score**: 4/5 | **빈출**: high | **출처**: [링크](https://www.it-server-room.com/2025/07/02/)

**모범 답변:**
애니메이션은 `top/left` 대신 `transform`, `opacity`를 써서 Layout·Paint를 건너뛰고 GPU가 처리하는 Composite 단계만 타게 합니다.
DOM 변경은 `DocumentFragment`나 클래스 일괄 변경으로 묶고, 레이아웃 값 읽기·쓰기를 섞지 않아 강제 동기 레이아웃(layout thrashing)을 피합니다.
자주 움직이는 요소엔 `will-change`로 별도 레이어를 만들되 남용하면 메모리가 늘어나므로 주의합니다.
```js
// 나쁨: 읽기/쓰기 반복 → 매번 리플로우
items.forEach(el => { el.style.width = box.offsetWidth + 'px'; });
// 좋음: 한 번 읽고 일괄 쓰기
const w = box.offsetWidth; items.forEach(el => { el.style.width = w + 'px'; });
```

### Q5. script 태그의 async와 defer 차이, 그리고 스크립트가 HTML 파싱을 막는 이유를 설명해 주세요.

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/baeharam/Must-Know-About-Frontend)

**모범 답변:**
JS는 `document.write`나 DOM 조작으로 문서 구조를 바꿀 수 있어서, 일반 `<script>`를 만나면 파서가 멈추고 다운로드·실행이 끝난 뒤 파싱을 이어갑니다.
`async`는 파싱과 병렬로 다운로드하고 완료 즉시 실행하므로 실행 순서가 보장되지 않습니다(광고·분석 스크립트에 적합).
`defer`는 병렬 다운로드 후 HTML 파싱이 끝나면 문서 순서대로, `DOMContentLoaded` 직전에 실행됩니다(DOM에 의존하는 앱 코드에 적합).
