### Q1. any와 unknown의 차이점은 무엇인가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@moonheekim0118/%ED%83%80%EC%9E%85%EC%8A%A4%ED%81%AC%EB%A6%BD%ED%8A%B8-any-unknown-%EA%B7%B8%EB%A6%AC%EA%B3%A0-never-%EC%9D%98-%EC%B0%A8%EC%9D%B4%EC%A0%90)

**모범 답변:**
any는 타입 검사를 사실상 무력화하여 모든 연산이 허용되지만, unknown은 어떤 값이든 할당받을 수는 있어도 사용 전에 반드시 타입을 좁혀야 한다. 즉 unknown은 "타입은 모르지만 안전하게 다루고 싶다"는 의도를 표현하며, typeof/instanceof 등으로 검증한 뒤에만 프로퍼티 접근이나 연산이 가능하다. 외부 API 응답처럼 타입을 확신할 수 없는 값을 다룰 때는 any 대신 unknown을 사용해 컴파일 타임 타입 안전성을 확보하는 것이 권장된다.

### Q2. 제네릭(Generic)이란 무엇이며 왜 사용하나요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@minbr0ther/%EB%B2%88%EC%97%AD-%ED%83%80%EC%9E%85%EC%8A%A4%ED%81%AC%EB%A6%BD%ED%8A%B8-%EB%A9%B4%EC%A0%91%EC%9D%B8%ED%84%B0%EB%B7%B0-%EC%A7%88%EB%AC%B8-%EC%8B%9C%EB%A6%AC%EC%A6%88-1)

**모범 답변:**
제네릭은 함수·클래스·인터페이스를 선언할 때 타입을 고정하지 않고, 사용 시점에 타입 파라미터(T 등)로 지정해 재사용성과 타입 안전성을 동시에 확보하는 기법이다. any와 달리 제네릭은 입력 타입과 출력 타입의 관계를 컴파일러가 추론·검증할 수 있어 반환값의 타입 정보를 잃지 않는다. 예를 들어 `function identity<T>(arg: T): T { return arg }`처럼 다양한 타입에서 동작하면서도 타입 정보를 유지하는 재사용 가능한 유틸/컴포넌트를 만들 때 사용한다.

### Q3. 타입 가드(Type Guard)란 무엇이며 어떻게 구현하나요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://chanhuiseok.github.io/posts/ts-2/)

**모범 답변:**
타입 가드는 조건문 내에서 typeof, instanceof, in 연산자나 사용자 정의 타입 predicate(`value is Type`)를 이용해 변수의 타입을 특정 블록 안에서 좁혀주는 기법이다. 컴파일러가 타입 가드 이후의 코드 흐름에서 좁혀진 타입을 인식하므로, 불필요한 타입 단언(as) 없이 안전하게 프로퍼티나 메서드에 접근할 수 있다. 실무에서는 API 응답이나 유니온 타입으로 정의된 상태값을 처리할 때 분기별로 타입 가드를 적용해 런타임 에러를 방지한다.

### Q4. 타입 좁히기(Type Narrowing)는 어떻게 이루어지며 typeof/instanceof는 어떤 차이가 있나요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@boyeon_jeong/%ED%83%80%EC%9E%85%EC%8A%A4%ED%81%AC%EB%A6%BD%ED%8A%B8-%EB%AC%B8%EC%A0%9C)

**모범 답변:**
타입 좁히기는 유니온 타입처럼 여러 타입을 가질 수 있는 변수를, 조건문을 통해 특정 시점에 더 구체적인 타입으로 컴파일러가 추론하게 만드는 과정이다. typeof는 string/number/boolean 등 원시 타입을 구분할 때 쓰고, instanceof는 클래스 인스턴스처럼 프로토타입 체인을 가진 객체 타입을 구분할 때 사용한다. 두 연산자 모두 런타임에 실제로 평가되므로, 타입스크립트는 그 결과를 바탕으로 이후 코드 블록에서 변수의 타입을 안전하게 좁혀 추론한다.

### Q5. TypeScript에서 enum 대신 as const를 사용하는 것이 권장되는 이유는 무엇인가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://engineering.linecorp.com/ko/blog/typescript-enum-tree-shaking)

**모범 답변:**
TypeScript의 enum은 컴파일 시 즉시실행함수(IIFE) 형태의 자바스크립트 코드로 변환되는데, 번들러가 이를 사용하지 않는 코드로 판단하지 못해 Tree-shaking이 되지 않아 번들 크기가 커진다. 반면 `as const`로 객체를 선언하면 각 프로퍼티가 리터럴 타입으로 고정되어 enum과 유사한 타입 안전성을 얻으면서도, 트랜스파일 결과가 순수 객체 리터럴이라 불필요한 코드 생성 없이 Tree-shaking이 가능하다. 그래서 번들 크기와 성능이 중요한 프로덕션 코드에서는 enum보다 `as const` + 유니온 타입 조합이 권장된다.
