### Q1. CRP(Critical Rendering Path)란 무엇인가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://raw.githubusercontent.com/Esoolgnah/Frontend-Interview-Questions/main/Notes/important-5/browser-rendering.md)

**모범 답변:**
CRP는 브라우저가 HTML·CSS·JS를 받아 실제 픽셀로 화면에 그려내기까지의 일련의 단계(DOM/CSSOM 생성 → 렌더트리 구성 → Layout → Paint)를 말합니다.
이 경로를 최적화하면 초기 렌더링 속도가 빨라지므로, 렌더링 차단 리소스(CSS)를 줄이고 JS를 defer/async로 로드하는 것이 핵심 전략입니다.
크리티컬 CSS만 먼저 인라인으로 제공하고 나머지는 비동기로 로드하는 방식도 CRP 최적화의 대표적인 예입니다.

### Q2. Reflow와 Repaint가 실행되는 시점은 언제인가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://raw.githubusercontent.com/Esoolgnah/Frontend-Interview-Questions/main/Notes/important-5/reflow-repaint.md)

**모범 답변:**
Reflow는 DOM 요소의 추가·제거, 크기·위치 변경 등 레이아웃에 영향을 주는 변경이 있을 때 발생하며, 영향받은 노드들의 레이아웃을 재계산합니다.
Repaint는 opacity, background-color처럼 레이아웃에는 영향 없이 시각적 표현만 바뀔 때 발생하고, Reflow 이후에 항상 뒤따라 실행됩니다.
offsetWidth/offsetHeight 같은 속성을 읽는 것만으로도 강제 Reflow(Layout Thrashing)가 트리거될 수 있어 주의가 필요합니다.

### Q3. 주소창에 google.com을 입력하면 일어나는 일을 설명해주세요

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://raw.githubusercontent.com/Esoolgnah/Frontend-Interview-Questions/main/Notes/important-5/what-happens-when-type-google.md)

**모범 답변:**
먼저 DNS 조회를 통해 도메인을 IP 주소로 변환하고, 브라우저는 해당 IP로 서버와 TCP 연결을 맺습니다.
연결이 수립되면 HTTP 요청 메시지를 생성해 서버로 전송하고, 서버는 이에 대한 응답(HTML 등)을 반환합니다.
마지막으로 브라우저가 응답을 파싱해 DOM/CSSOM을 만들고 렌더트리를 구성해 화면에 그려냅니다.

### Q4. LocalStorage, SessionStorage, 쿠키의 차이점은 무엇인가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://raw.githubusercontent.com/Esoolgnah/Frontend-Interview-Questions/main/Notes/important-4/web-storage.md)

**모범 답변:**
LocalStorage는 만료 기한 없이 데이터를 영구 보관하며 용량은 약 5MB이고, 명시적으로 지우기 전까지 유지됩니다.
SessionStorage는 브라우저 탭(세션)이 종료되면 자동으로 삭제되며 용량은 LocalStorage와 동일하게 약 5MB입니다.
쿠키는 용량이 약 4KB로 작지만 모든 HTTP 요청에 자동으로 포함되어 전송되므로, 인증 토큰처럼 서버와 주고받아야 하는 정보에 주로 사용됩니다.

### Q5. CORS란 무엇이고 왜 필요한가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://raw.githubusercontent.com/Esoolgnah/Frontend-Interview-Questions/main/Notes/important-3/how-to-handle-cors-error.md)

**모범 답변:**
CORS(Cross-Origin Resource Sharing)는 브라우저가 다른 출처(origin)의 서버 리소스에 접근할 수 있도록 허용 여부를 표준화한 스펙입니다.
브라우저의 동일 출처 정책(Same-Origin Policy)으로 인해 기본적으로 교차 출처 요청은 차단되며, 서버가 `Access-Control-Allow-Origin` 등의 응답 헤더로 명시적으로 허용해야 통신이 가능합니다.
이는 악의적인 사이트가 사용자 몰래 다른 도메인의 리소스에 접근하는 것을 막기 위한 보안 장치입니다.
