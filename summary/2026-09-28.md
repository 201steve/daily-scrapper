### Q1. 브라우저의 렌더링 원리(DOM/CSSOM/Render Tree/Layout/Paint)를 설명해주세요

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/Esoolgnah/Frontend-Interview-Questions/blob/main/Notes/important-5/browser-rendering.md)

**모범 답변:**
브라우저는 HTML을 파싱해 DOM 트리를, CSS를 파싱해 CSSOM 트리를 만든 뒤 두 트리를 결합해 실제로 화면에 그려질 노드만 포함하는 Render Tree를 구성합니다. 이후 Layout 단계에서 각 노드의 위치와 크기를 계산하고, Paint 단계에서 실제 픽셀을 그리며, 마지막으로 여러 레이어를 합성(Composite)합니다. `display: none` 요소는 Render Tree에서 제외되지만 `visibility: hidden` 요소는 공간을 차지하므로 포함됩니다.

### Q2. Reflow와 Repaint가 실행되는 시점과 차이는 무엇인가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/Esoolgnah/Frontend-Interview-Questions/blob/main/Notes/important-5/reflow-repaint.md)

**모범 답변:**
리플로우는 요소의 크기·위치가 바뀌어 레이아웃을 다시 계산하는 것이고, 리페인트는 레이아웃에는 영향을 주지 않는 색상·배경 등 시각적 변화만 다시 그리는 것입니다. 리플로우가 발생하면 항상 리페인트도 함께 일어나지만 역은 성립하지 않습니다. `offsetWidth` 같은 값을 반복 조회하거나 DOM을 여러 번 변경하면 리플로우가 반복 발생해 성능이 저하되므로, 클래스 일괄 변경이나 `transform`/`opacity` 사용 등으로 최소화합니다.

### Q3. 브라우저 주소창에 URL을 입력하면 일어나는 일을 설명해주세요

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/Esoolgnah/Frontend-Interview-Questions/blob/main/Notes/important-5/what-happens-when-type-google.md)

**모범 답변:**
주소창에 입력 후 브라우저는 DNS 조회로 도메인을 IP로 변환하고, 서버와 TCP(및 TLS) 연결을 맺은 뒤 HTTP 요청을 보냅니다. 서버가 응답을 반환하면 브라우저는 HTML을 파싱해 DOM/CSSOM을 만들고 Render Tree → Layout → Paint 과정을 거쳐 화면에 렌더링합니다. DNS, TCP/TLS 핸드셰이크, HTTP, 렌더링까지 전체 흐름을 설명할 수 있어야 네트워크와 브라우저 지식을 함께 검증할 수 있습니다.

### Q4. CSR(Client Side Rendering)과 SSR(Server Side Rendering)의 차이는 무엇인가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@ahsy92/%EA%B8%B0%EC%88%A0%EB%A9%B4%EC%A0%91-CSR%EA%B3%BC-SSR)

**모범 답변:**
CSR은 브라우저가 최소한의 HTML과 JS 번들을 받아 클라이언트에서 렌더링하는 방식으로, 초기 로딩은 느리지만 이후 페이지 전환이 빠르고 서버 부담이 적습니다. SSR은 서버에서 완성된 HTML을 렌더링해 보내므로 최초 콘텐츠 노출(FCP)이 빠르고 SEO에 유리하지만, 매 요청마다 서버 렌더링 비용이 발생합니다. Next.js 같은 프레임워크는 두 방식을 라우트 단위로 혼용해 트레이드오프를 절충합니다.

### Q5. CORS(Cross-Origin Resource Sharing)란 무엇이며 브라우저는 이를 어떻게 처리하나요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@effirin/CORS%EB%9E%80-%EB%AC%B4%EC%97%87%EC%9D%B8%EA%B0%80)

**모범 답변:**
CORS는 브라우저가 다른 출처(origin)의 리소스 요청을 허용할지 판단하는 보안 정책으로, 서버가 `Access-Control-Allow-Origin` 등의 응답 헤더로 허용 출처를 지정합니다. 요청 자체는 서버까지 도달하지만, 허용 헤더가 없으면 브라우저가 응답을 차단해 스크립트가 결과에 접근하지 못하게 합니다. 따라서 CORS 문제는 프론트엔드 코드만으로 해결할 수 없고 서버의 헤더 설정이나 프록시를 통해 해결해야 합니다.
