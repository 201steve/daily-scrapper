### Q1. CORS란 무엇이며 왜 발생하나요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@holim0/Front-End-%EB%A9%B4%EC%A0%91-%EC%A7%88%EB%AC%B8-%EB%8C%80%EB%B9%84-Part3)

**모범 답변:**
CORS는 브라우저의 동일 출처 정책(Same-Origin Policy) 때문에 프로토콜·도메인·포트 중 하나라도 다른 출처로의 요청이 기본적으로 차단되면서 발생하는 문제다. 서버가 응답 헤더에 `Access-Control-Allow-Origin` 등을 설정해 특정 출처를 허용하면 브라우저가 이를 확인하고 응답을 전달해준다. 개발 단계에서는 프론트엔드 서버 앞에 프록시를 두어 요청을 동일 출처처럼 보이게 우회하기도 한다.

### Q2. 브라우저 주소창에 URL을 입력했을 때 일어나는 일을 설명해주세요 (DNS 조회, TCP 연결, HTTP 요청/응답 과정 포함)

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@seungmini/%ED%94%84%EB%A1%A0%ED%8A%B8%EC%97%94%EB%93%9C-%EB%A9%B4%EC%A0%91-%EC%A7%88%EB%AC%B8-%EB%B0%8F-%EB%8B%B5%EB%B3%80-0)

**모범 답변:**
먼저 브라우저 캐시 → OS 캐시 → 라우터 캐시 → ISP DNS 서버 순으로 도메인에 해당하는 IP를 찾는 DNS 조회가 이루어진다. IP를 얻으면 TCP 3-way handshake로 서버와 연결을 맺고, HTTPS라면 TLS 핸드셰이크로 암호화 연결까지 수립한다. 이후 HTTP 요청을 전송하고 서버 응답(HTML 등)을 받으면 브라우저가 파싱·렌더링을 시작한다.

### Q3. HTTP와 HTTPS의 차이는 무엇인가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://joontae-kim.github.io/2020/10/26/interview-question-network/)

**모범 답변:**
HTTP는 80번 포트를 사용해 평문으로 통신하는 프로토콜이고, HTTPS는 여기에 SSL/TLS 암호화 계층을 추가해 443번 포트로 통신한다. HTTPS는 대칭키·공개키 방식을 함께 사용해 데이터 기밀성과 무결성, 서버 인증을 보장한다. 로그인 정보나 개인정보를 다루는 서비스는 반드시 HTTPS를 적용해야 한다.

### Q4. HTTP 캐싱에서 Cache-Control 헤더는 어떻게 활용하나요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://feel5ny.github.io/2019/10/05/HTTP_007-2/)

**모범 답변:**
Cache-Control 헤더는 브라우저와 중간 서버가 리소스를 어떻게 캐싱할지 제어한다. 배포마다 내용이 바뀌는 HTML 같은 리소스는 `max-age=0`으로 항상 최신 여부를 재확인하게 하고, 해시가 붙는 정적 자산(JS/CSS)은 `max-age=31536000`처럼 길게 캐싱해 성능을 높인다. `no-cache`는 캐시를 저장하되 매번 서버에 유효성 검증을 요청하고, `no-store`는 아예 저장 자체를 막는다는 차이가 있다.

### Q5. 세션(Session) 방식과 JWT(토큰) 방식의 차이는 무엇인가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://joontae-kim.github.io/2020/10/26/interview-question-list/)

**모범 답변:**
Session 방식은 서버 메모리(혹은 DB)에 사용자 상태를 저장하고 클라이언트에는 세션 ID만 쿠키로 내려줘 매 요청마다 서버가 상태를 조회한다. JWT는 필요한 사용자 정보를 payload에 담아 서명한 토큰 자체를 클라이언트가 들고 다니므로 서버가 별도 저장소를 조회할 필요가 없어 확장성에 유리하다. 다만 발급 후 즉시 무효화가 어렵다는 단점이 있어 만료 시간 설정과 리프레시 토큰 전략이 함께 필요하다.
