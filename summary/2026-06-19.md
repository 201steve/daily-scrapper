### Q1. CORS(Cross-Origin Resource Sharing)란 무엇이며, 어떻게 해결하는가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [Esoolgnah/Frontend-Interview-Questions](https://github.com/Esoolgnah/Frontend-Interview-Questions)

**모범 답변:**
CORS는 브라우저가 다른 출처(프로토콜+호스트+포트 조합)의 리소스 요청을 차단하는 보안 정책이다. 서버가 `Access-Control-Allow-Origin` 헤더로 허용 출처를 명시해야 브라우저가 응답을 허용한다. 프론트엔드에서는 개발 시 Vite/Webpack 프록시로 우회하고, 프로덕션에서는 백엔드에 CORS 미들웨어를 설정하거나 API Gateway 수준에서 처리한다.

### Q2. HTTP와 HTTPS의 차이점은 무엇인가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [Esoolgnah/Frontend-Interview-Questions](https://github.com/Esoolgnah/Frontend-Interview-Questions)

**모범 답변:**
HTTP는 평문으로 데이터를 전송하지만, HTTPS는 TLS(Transport Layer Security) 암호화를 추가해 도청·변조를 방지한다. HTTPS는 443번 포트를 사용하며, 서버의 SSL/TLS 인증서를 통해 서버 신원도 검증한다. 브라우저는 HTTPS 환경에서만 Service Worker, Geolocation 등 일부 보안 민감 Web API를 허용한다.

### Q3. Preflight Request란 무엇이며 왜 필요한가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [da-in/tech-interview-study — CORS.md](https://github.com/da-in/tech-interview-study/blob/main/CS%20Deep%20Dive/Web/CORS.md)

**모범 답변:**
Preflight는 실제 요청 전 브라우저가 `OPTIONS` 메서드로 서버에 사전 허가를 요청하는 절차다. Simple Request 조건(GET·POST·HEAD + 단순 헤더 + 단순 Content-Type)을 벗어나면 자동으로 발생한다. 서버는 `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`로 허용 범위를 응답하며, `Access-Control-Max-Age`를 설정해 반복 Preflight 비용을 줄일 수 있다.

### Q4. JWT(JSON Web Token)와 세션(Session) 기반 인증의 차이점은?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [rlagurwns112 — 네트워크 면접 질문 정리](https://velog.io/@rlagurwns112/%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC-%EB%A9%B4%EC%A0%91-%EC%A7%84%EB%AC%B8-%EC%A0%95%EB%A6%AC)

**모범 답변:**
Session은 서버가 세션 정보를 저장하고 클라이언트에 세션 ID만 쿠키로 전달해 매 요청마다 서버 조회가 필요하다. JWT는 인증 정보를 토큰 자체에 서명(Signature)과 함께 담아 서버가 별도 저장소 없이 검증하므로(Stateless) 수평 확장에 유리하다. 단, JWT는 만료 전 무효화가 어려워 탈취 위험이 있으므로 단기 Access Token + 장기 Refresh Token 전략을 함께 사용한다.

### Q5. XSS(Cross-Site Scripting)와 CSRF(Cross-Site Request Forgery)란 무엇인가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [doheek2 — 프론트엔드 기술 면접 질문 리스트](https://velog.io/@doheek2/%ED%94%84%EB%A1%A0%ED%8A%B8%EC%97%94%EB%93%9C-%EA%B8%B0%EC%88%A0-%EB%A9%B4%EC%A0%91-%EC%A7%88%EB%AC%B8-%EB%A6%AC%EC%8A%A4%ED%8A%B8)

**모범 답변:**
XSS는 공격자가 악성 스크립트를 페이지에 삽입해 피해자 브라우저에서 실행시키는 공격으로, 쿠키·세션 탈취에 주로 악용된다. 방어: 사용자 입력 이스케이프, `innerHTML` 사용 지양, `Content-Security-Policy` 헤더 설정. CSRF는 인증된 사용자가 의도하지 않은 요청을 보내도록 유도하는 공격이다. 방어: CSRF Token 발급·검증, `SameSite=Strict` 쿠키 속성, Origin/Referer 헤더 검증.
