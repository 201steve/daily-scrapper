### Q1. 브라우저 주소창에 URL을 입력하면 어떤 일이 일어나나요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/baeharam/Must-Know-About-Frontend)

**모범 답변:**
브라우저는 URL을 파싱한 뒤 브라우저·OS 캐시 → DNS 서버 순으로 도메인의 IP를 조회합니다.
IP를 얻으면 TCP 3-way handshake로 연결하고, HTTPS라면 TLS 핸드셰이크로 암호화 채널을 맺습니다.
이후 HTTP 요청을 보내고, 서버는 상태 코드·헤더·본문(HTML)을 응답합니다.
브라우저는 HTML/CSS를 파싱해 DOM·CSSOM → 렌더 트리 → 레이아웃 → 페인트 순으로 화면을 그립니다.
실무에서는 각 단계가 DNS prefetch, preconnect, CDN, HTTP 캐시 같은 최적화 포인트가 됩니다.

### Q2. CORS가 무엇인가요? 직접 겪고 해결해 본 경험이 있나요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/junh0328/prepare_frontend_interview)

**모범 답변:**
CORS는 동일 출처 정책(SOP) 때문에 막히는 다른 출처(스킴·호스트·포트 중 하나라도 다름) 요청을, 서버가 응답 헤더로 허용해 주는 메커니즘입니다.
브라우저는 응답의 `Access-Control-Allow-Origin` 등을 확인해 허용되지 않으면 JS에 응답을 노출하지 않습니다.
비단순 요청(PUT/DELETE, `Content-Type: application/json`, 커스텀 헤더 등)은 먼저 OPTIONS preflight를 보냅니다.
해결은 서버에서 허용 Origin·메서드·헤더를 설정하는 게 정석이고, 개발 환경에서는 Vite/webpack dev server proxy로 우회합니다.
쿠키를 함께 보낼 땐 `credentials: 'include'` + `Access-Control-Allow-Credentials: true` + 와일드카드가 아닌 명시적 Origin이 필요합니다.

### Q3. HTTPS는 HTTP와 무엇이 다른가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/junh0328/prepare_frontend_interview)

**모범 답변:**
HTTP는 평문으로 전송돼 도청·변조·위장에 취약하고, HTTPS는 HTTP를 SSL/TLS 위에서 동작시켜 이를 보완합니다.
HTTPS는 암호화(기밀성), 무결성(MAC으로 변조 검출), 인증(CA가 서명한 인증서로 서버 신원 확인) 세 가지를 제공합니다.
TLS 핸드셰이크에서 비대칭키로 안전하게 세션키를 교환한 뒤, 실제 데이터는 빠른 대칭키로 암호화합니다.
실무에서는 Secure 쿠키, HTTP/2, Service Worker 등이 HTTPS를 전제로 하므로 사실상 필수입니다.

### Q4. HTTP 캐시란 무엇이고, 캐시 관련 헤더(Cache-Control 등)를 설명해주세요.

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/junh0328/prepare_frontend_interview)

**모범 답변:**
HTTP 캐시는 브라우저나 중간 프록시/CDN이 응답 사본을 저장해 재요청 없이 재사용함으로써 지연과 트래픽을 줄이는 기법입니다.
`Cache-Control: max-age=N`으로 신선도 기간을 정하며, `max-age`가 있으면 `Expires`는 무시됩니다. `no-cache`는 매번 재검증, `no-store`는 저장 금지입니다.
만료 후에는 `ETag`/`If-None-Match` 또는 `Last-Modified`/`If-Modified-Since`로 재검증하고, 변경이 없으면 `304 Not Modified`를 받습니다.
실무 패턴: 해시가 붙은 정적 파일은 `max-age=31536000, immutable`, HTML은 `no-cache`로 배포 즉시 반영합니다.

### Q5. 쿠키와 세션의 차이는 무엇인가요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/baeharam/Must-Know-About-Frontend)

**모범 답변:**
HTTP는 무상태(stateless)라 사용자 상태 유지를 위해 쿠키·세션을 씁니다.
쿠키는 클라이언트(브라우저)에 저장되어 요청마다 자동 전송되는 작은 데이터이고, 세션은 서버에 상태를 저장하고 클라이언트에는 세션 ID만 쿠키로 둡니다.
세션은 민감 정보가 서버에 있어 상대적으로 안전하지만 서버 메모리/저장소 부담과 수평 확장 시 세션 공유 문제가 있습니다.
쿠키 보안은 `HttpOnly`(XSS로 탈취 방지), `Secure`(HTTPS 전용), `SameSite`(CSRF 완화) 속성으로 강화합니다.
