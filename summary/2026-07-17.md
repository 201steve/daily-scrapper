### Q1. 주소창에 URL을 입력하면 어떤 과정을 거쳐 화면에 렌더링되는가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/Esoolgnah/Frontend-Interview-Questions)

**모범 답변:**
브라우저가 URL을 파싱하고 DNS 조회(브라우저 → OS → 라우터 → ISP 캐시 순)로 도메인의 IP 주소를 확인한다. 확인된 IP로 서버와 TCP 연결(3-way handshake)을 맺고, HTTPS라면 TLS 핸드셰이크도 수행한다. 브라우저가 HTTP 요청을 보내면 서버는 응답으로 HTML을 반환하며, 브라우저는 이를 파싱해 DOM/CSSOM과 렌더 트리를 구성한 뒤 레이아웃·페인트 과정을 거쳐 화면에 그린다.

### Q2. CORS란 무엇이며 왜 필요한가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/da-in/tech-interview-study/blob/main/CS%20Deep%20Dive/Web/CORS.md)

**모범 답변:**
CORS(Cross-Origin Resource Sharing)는 브라우저가 다른 출처(origin)의 리소스에 접근하는 것을 서버가 명시적으로 허용하도록 하는 HTTP 헤더 기반 메커니즘이다. 브라우저는 기본적으로 동일 출처 정책(SOP)에 따라 프로토콜·호스트·포트가 다른 출처로의 응답 접근을 차단하는데, 이는 CSRF·XSS 같은 공격을 막기 위함이다. 서버가 `Access-Control-Allow-Origin` 등의 응답 헤더로 허용 출처를 명시하면 브라우저가 이를 검사해 접근 허용 여부를 판단한다.

### Q3. CORS Preflight Request는 언제 발생하며 어떻게 동작하는가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://joontae-kim.github.io/2020/10/26/interview-question-fe/)

**모범 답변:**
Preflight Request는 실제 요청 전에 브라우저가 자동으로 보내는 사전 확인 요청으로, HTTP `OPTIONS` 메서드를 사용한다. 단순 요청 범위를 벗어난 메서드(PUT/DELETE 등)나 커스텀 헤더, `Content-Type: application/json` 등을 사용할 때 발생한다. `Access-Control-Request-Method`, `Access-Control-Request-Headers` 헤더로 실제 요청 정보를 담아 보내고, 서버가 이를 허용하는 `Access-Control-Allow-*` 응답을 줘야 실제 요청이 전송된다. `Access-Control-Max-Age`로 이 사전 확인 결과의 캐싱 시간을 지정할 수 있다.

### Q4. RESTful API란 무엇이며, HTTP 메서드(GET, POST, PUT, PATCH, DELETE)의 차이는?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/Esoolgnah/Frontend-Interview-Questions)

**모범 답변:**
RESTful API는 자원을 URI로 표현하고, HTTP 메서드로 해당 자원에 대한 행위를 표현하는 아키텍처 스타일이다. GET은 자원 조회(멱등, 캐시 가능), POST는 새로운 자원 생성(비멱등), PUT은 자원 전체 교체(멱등), PATCH는 자원 일부 수정, DELETE는 자원 삭제(멱등)를 의미한다. 프론트엔드에서는 요청 목적에 맞는 메서드를 선택해 서버와 명확한 의도를 주고받는 것이 중요하다.

### Q5. 쿠키, 세션, 토큰(JWT)의 차이는 무엇인가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@jiwoow00/%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC-%EC%BF%A0%ED%82%A4-%EC%84%B8%EC%85%98-%ED%86%A0%ED%81%B0-REST)

**모범 답변:**
HTTP는 상태를 유지하지 않는(stateless) 프로토콜이라, 로그인 상태를 기억하려면 쿠키·세션·토큰 같은 별도 수단이 필요하다. 쿠키는 클라이언트에 데이터를 저장해 매 요청마다 함께 전송하며 서버 자원은 쓰지 않지만 탈취·변조에 취약하다. 세션은 실제 데이터를 서버에 저장하고 클라이언트는 세션 ID만 쿠키로 들고 있어 보안은 낫지만 서버 자원을 소모한다. 토큰(JWT)은 필요한 정보를 암호화해 토큰 자체에 담아 클라이언트가 보관하므로 서버가 별도 저장소 없이 검증만 하면 되어 확장성이 좋지만, 탈취 시 만료 전까지 무효화가 어렵다.
