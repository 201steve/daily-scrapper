### Q1. 웹 통신의 큰 흐름: https://www.google.com/ 을 접속할 때 일어나는 일을 설명해보세요.

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/ksundong/backend-interview-question)

**모범 답변:**
URL 입력 → 브라우저 캐시/DNS 조회로 IP 획득 → TCP 3-way handshake → HTTPS면 TLS handshake → HTTP 요청 전송 → 서버 응답(HTML) 수신 → 파싱·렌더링(DOM/CSSOM → Render Tree → Layout → Paint) 순으로 진행됩니다. 이후 HTML 안의 JS/CSS/이미지 리소스도 같은 과정으로 추가 요청합니다. 각 단계의 병목(DNS, 연결, TTFB)이 초기 로딩 성능에 직결됩니다.

### Q2. CORS란 무엇이며, 왜 발생하고 어떻게 해결하나요?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/WeareSoft/tech-interview)

**모범 답변:**
CORS(Cross-Origin Resource Sharing)는 출처(scheme+host+port)가 다른 리소스 요청을 서버가 허용하는지 브라우저가 검사하는 정책입니다. 동일 출처 정책(SOP) 때문에 다른 출처 응답을 JS가 읽을 수 없어 에러가 발생합니다. 해결은 서버가 `Access-Control-Allow-Origin` 등 헤더를 내려주는 것이 원칙이고, 개발 중에는 프록시를 쓸 수 있습니다. PUT/커스텀 헤더 등은 OPTIONS preflight 요청이 먼저 나갑니다.

### Q3. HTTP와 HTTPS의 차이점에 대해 설명해보세요.

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/JaeYeopHan/Interview_Question_for_Beginner)

**모범 답변:**
HTTP는 평문 통신이라 도청·변조·위장에 취약하고, HTTPS는 TLS 위에서 암호화(기밀성), 무결성, 인증서 기반 서버 인증을 제공합니다. TLS handshake에서 인증서를 검증하고 대칭키를 협상한 뒤 대칭키로 데이터를 암호화합니다. 기본 포트는 80/443이며, HTTP/2 이상과 최신 브라우저 API(Service Worker 등)는 HTTPS를 요구합니다.

### Q4. GET과 POST의 차이점에 대해 설명해보세요.

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/ksundong/backend-interview-question)

**모범 답변:**
GET은 리소스 조회용으로 멱등·안전하며 파라미터를 URL 쿼리로 전달하고 캐싱될 수 있습니다. POST는 리소스 생성·처리용으로 데이터를 body에 담고 멱등하지 않으며 기본적으로 캐싱되지 않습니다. body가 URL이 아니라서 로그/히스토리 노출이 적지만, 그 자체로 암호화는 아니므로 보안은 HTTPS로 확보해야 합니다.

### Q5. TCP와 UDP의 차이점에 대해 설명해보세요.

> **importance_score**: 2/5 | **빈출**: high | **출처**: [링크](https://github.com/JaeYeopHan/Interview_Question_for_Beginner)

**모범 답변:**
TCP는 연결 지향으로 3-way handshake, 순서 보장, 재전송, 흐름·혼잡 제어를 제공해 신뢰성이 높고 상대적으로 느립니다. UDP는 비연결형으로 헤더가 작고 빠르지만 순서·유실을 보장하지 않습니다. HTTP/1.1·2는 TCP, HTTP/3(QUIC)는 UDP 위에서 동작하며, 실시간 스트리밍·게임·DNS에 UDP가 쓰입니다.
