### Q1. TCP의 3-way-handshake와 4-way-handshake 과정을 설명하라

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@leeesangheee/%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC.-TCP-3-way-Handshake)

**모범 답변:**
3-way handshake는 TCP 연결 수립 과정으로, 클라이언트가 SYN을 보내고 서버가 SYN+ACK로 응답한 뒤 클라이언트가 다시 ACK를 보내 연결을 확립한다. 이 과정에서 양쪽의 송수신 준비 상태를 확인하고 초기 시퀀스 번호를 교환해 신뢰성 있는 통신을 보장한다. 4-way handshake는 연결 종료 과정으로, FIN → ACK → FIN → ACK 순서로 양쪽이 각각 종료 의사를 확인하며, 이후 TIME_WAIT 상태를 거쳐 지연된 패킷을 처리한 뒤 완전히 닫힌다.

### Q2. 쿠키, 세션, 토큰의 차이는 무엇인가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@jung5318/%EC%BF%A0%ED%82%A4-%EC%84%B8%EC%85%98-%ED%86%A0%ED%81%B0%EC%9D%98-%EC%B0%A8%EC%9D%B4%EC%A0%90)

**모범 답변:**
HTTP는 무상태(Stateless) 프로토콜이라 사용자 상태를 별도로 관리해야 한다. 쿠키는 클라이언트(브라우저)에 데이터를 저장하고, 세션은 서버에 사용자 정보를 저장한 뒤 클라이언트에는 세션 ID만 쿠키로 전달한다. 토큰(JWT 등)은 사용자 정보를 토큰 자체에 담아 클라이언트가 보관하므로 서버가 별도 저장소를 관리할 필요가 없지만, 토큰 크기가 커지고 즉시 폐기가 어렵다는 단점이 있다. 실무에서는 보안 요구 수준과 서버 확장성(stateless 여부)을 고려해 방식을 선택한다.

### Q3. CORS란 무엇이며 왜 발생하는가? 해결 방법은 무엇인가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@holim0/Front-End-%EB%A9%B4%EC%A0%91-%EC%A7%88%EB%AC%B8-%EB%8C%80%EB%B9%84-Part3)

**모범 답변:**
CORS는 브라우저의 동일 출처 정책(Same-Origin Policy) 때문에 다른 출처(프로토콜+도메인+포트가 다른)의 리소스에 접근할 때 발생하는 제약을 서버가 명시적으로 허용해주는 메커니즘이다. 브라우저가 요청 시 Origin 헤더를 보내면 서버가 Access-Control-Allow-Origin 등의 응답 헤더로 허용 여부를 알려준다. CORS 에러는 프론트엔드 코드만으로는 해결할 수 없고, 백엔드에서 CORS 헤더를 설정하거나 프록시 서버를 경유해야 한다. 실무에서는 개발 환경에서 프록시 설정으로 우회하고, 배포 환경에서는 서버 측 헤더 설정으로 해결하는 경우가 많다.

### Q4. 브라우저 주소창에 URL을 입력하면 일어나는 일을 설명하라

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@gyumin_2/%EB%B8%8C%EB%9D%BC%EC%9A%B0%EC%A0%80-%EB%8F%99%EC%9E%91-%EC%9B%90%EB%A6%AC-%EC%A3%BC%EC%86%8C%EC%B0%BD%EC%97%90-URL-%EC%9E%85%EB%A0%A5-%EC%8B%9C-%EC%9D%BC%EC%96%B4%EB%82%98%EB%8A%94-%EA%B3%BC%EC%A0%95%EB%B0%B0%EA%B2%BD%EC%A7%80%EC%8B%9D-%ED%8E%B8)

**모범 답변:**
브라우저에 URL을 입력하면 먼저 브라우저·OS·라우터·ISP 순으로 DNS 캐시를 확인해 도메인에 해당하는 IP 주소를 찾는다. 캐시에 없으면 DNS 서버에 쿼리를 보내 IP를 알아낸 뒤, 해당 서버와 TCP 3-way handshake로 연결을 수립한다(HTTPS라면 TLS 핸드셰이크가 추가된다). 연결이 수립되면 브라우저가 HTTP 요청을 보내고 서버가 응답을 반환하며, 브라우저는 받은 HTML을 파싱해 DOM/CSSOM을 구성하고 렌더링한다. 이 흐름을 이해하면 캐싱, CDN, 프리페치 등 성능 최적화 지점을 파악하는 데 도움이 된다.

### Q5. 도메인 입력 시 DNS가 IP 주소를 찾는 과정(DNS 캐시 조회 → ISP DNS 쿼리)을 설명하라

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@devjunehee/%EC%8B%A0%EC%9E%85-%ED%94%84%EB%A1%A0%ED%8A%B8%EC%97%94%EB%93%9C-%EB%A9%B4%EC%A0%91-%EC%A7%88%EB%AC%B8-%EB%A6%AC%EC%8A%A4%ED%8A%B8-CS-Network)

**모범 답변:**
도메인을 IP로 변환하는 DNS 조회는 브라우저 캐시 → OS 캐시 → 라우터 캐시 → ISP(Recursive) DNS 서버 순으로 진행되며, 캐시에 없으면 Root → TLD → Authoritative 네임서버를 순차적으로 거쳐 최종 IP를 찾는다. 조회된 결과는 TTL(Time To Live) 동안 각 단계 캐시에 저장되어 이후 요청 속도를 높인다. 프론트엔드 관점에서는 DNS 조회가 페이지 로딩의 첫 병목이 될 수 있어 dns-prefetch, preconnect 같은 리소스 힌트로 지연을 줄일 수 있다.
