### Q1. `interface`와 `type`의 차이점은 무엇인가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [Esoolgnah/Frontend-Interview-Questions](https://github.com/Esoolgnah/Frontend-Interview-Questions/blob/main/Notes/important-4/type-script.md)

**모범 답변:**
`interface`는 객체 타입만 정의할 수 있고, `type`은 원시값·유니온·인터섹션 등 모든 형태를 정의할 수 있다. `interface`는 동일 이름으로 **선언 병합(Declaration Merging)**이 가능하지만 `type`은 불가능하다. 확장 방식도 다르다 — `interface`는 `extends`, `type`은 `&` 인터섹션을 사용한다. 실무 컨벤션상 객체 형태에는 `interface`, 유니온·복잡한 조합에는 `type`을 권장한다.

### Q2. 제네릭(Generics)이란 무엇이며, `any`와의 차이점은 무엇인가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [2024-woowa-sahon-interview-study](https://github.com/woowacourse-study/2024-woowa-sahon-interview-study)

**모범 답변:**
제네릭은 타입을 매개변수처럼 사용해 재사용 가능한 함수·컴포넌트를 만드는 기법이다. `any`는 타입 검사를 완전히 포기하지만, 제네릭은 **호출 시점에 구체적인 타입이 결정**되어 타입 안전성을 유지한다.
```ts
function identity<T>(arg: T): T { return arg; }
// identity("hello") → T는 string으로 추론, 반환 타입도 string 보장
```
API 응답 타입이나 공통 훅(`useQuery<T>`)을 정의할 때 실무에서 필수적으로 활용된다.

### Q3. 유틸리티 타입(Utility Types)이란 무엇인가? 대표적인 예를 설명하라.

> **importance_score**: 3/5 | **빈출**: high | **출처**: [프론트엔드 기술 면접 질문 리스트](https://velog.io/@doheek2/%ED%94%84%EB%A1%A0%ED%8A%B8%EC%97%94%EB%93%9C-%EA%B8%B0%EC%88%A0-%EB%A9%B4%EC%A0%91-%EC%A7%88%EB%AC%B8-%EB%A6%AC%EC%8A%A4%ED%8A%B8)

**모범 답변:**
유틸리티 타입은 기존 타입을 변환·재활용하기 위한 내장 제네릭 타입들이다.
- `Partial<T>`: 모든 프로퍼티를 선택적(optional)으로 — 수정 API 요청 타입에 활용
- `Pick<T, K>` / `Omit<T, K>`: 특정 프로퍼티만 선택 / 제외 — 뷰 전용 타입 생성
- `Record<K, V>`: 키-값 쌍 타입 정의 — 코드 테이블, 상태 맵에 활용
- `Readonly<T>`: 모든 프로퍼티를 읽기 전용으로 — 불변 상태 표현

`type UpdateUser = Partial<User>`처럼 기존 타입에서 파생하여 중복 선언을 줄일 수 있다.

### Q4. `any`, `unknown`, `never` 타입의 차이점은 무엇인가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [타입스크립트에서 Any, Never, Unknown 활용법](https://f-lab.kr/insight/typescript-any-never-unknown-20240623)

**모범 답변:**
- **`any`**: 타입 검사를 완전히 비활성화. 어떤 타입이든 자유롭게 할당·사용 가능하지만 타입 안전성을 포기한다.
- **`unknown`**: 모든 값을 할당받을 수 있지만, 사용 전 반드시 타입 좁히기(Type Guard)가 필요. `any`의 안전한 대안.
- **`never`**: 절대 발생할 수 없는 값의 타입(예: 항상 예외를 던지는 함수). 유니온에서 모든 케이스를 처리한 후 남는 타입.

실무에서는 외부 API 응답을 `unknown`으로 수신 후 검증하는 패턴이 권장된다.

### Q5. 타입 가드(Type Guard)란 무엇이며, 어떤 방식으로 구현할 수 있는가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [면접 준비 노트 (TypeScript)](https://velog.io/@dnr6054/fe-interview-TypeScript)

**모범 답변:**
타입 가드는 런타임에 특정 타입인지 확인하여 컴파일러가 **타입을 좁히도록(narrowing)** 유도하는 기법이다.
- `typeof` — 원시 타입 확인: `if (typeof val === "string")`
- `instanceof` — 클래스 인스턴스 확인: `if (err instanceof Error)`
- `in` 연산자 — 프로퍼티 존재 여부: `if ("name" in obj)`
- **사용자 정의 타입 가드** — `is` 키워드 사용: `function isUser(obj: unknown): obj is User { ... }`

React에서 유니온 타입 컴포넌트 분기 처리나 `unknown` API 응답을 안전하게 다룰 때 필수적이다.
