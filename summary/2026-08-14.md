### Q1. CORS란 무엇이며 왜 발생하는가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/Esoolgnah/Frontend-Interview-Questions)

**모범 답변:**
CORS(Cross-Origin Resource Sharing)는 브라우저가 다른 출처(도메인·프로토콜·포트가 다른 리소스)로의 요청을 기본 차단하는 동일 출처 정책(Same-Origin Policy)을 완화해주는 메커니즘이다.
브라우저가 요청 시 Origin 헤더를 보내면 서버가 Access-Control-Allow-Origin 등의 응답 헤더로 허용 여부를 알려주고, 브라우저가 이를 검사해 응답 노출 여부를 결정한다.
PUT/DELETE처럼 상태를 변경하거나 커스텀 헤더가 포함된 요청은 실제 요청 전에 OPTIONS 메서드로 preflight 요청을 먼저 보내 허용 여부를 확인한다.
실무에서는 서버 CORS 헤더 설정 누락, 개발 서버 프록시 미설정 등으로 자주 마주치며, 백엔드 헤더 조정이나 프록시 서버로 해결한다.

### Q2. HTTP 캐시 관련 헤더(Cache-Control, ETag, Expires 등)에 대해 설명하라.

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/h5bp/Front-end-Developer-Interview-Questions/blob/main/src/translations/korean/README.md)

**모범 답변:**
Expires는 만료 절대 시각을, Cache-Control은 max-age·no-cache·no-store 등 세밀한 캐시 정책을 지정하며 HTTP/1.1 이후 Cache-Control이 우선 적용된다.
ETag는 리소스 콘텐츠의 해시값으로, 조건부 요청(If-None-Match)을 통해 리소스 변경 여부를 검증하고 변경이 없으면 304 Not Modified를 반환해 대역폭을 절약한다.
Last-Modified/If-Modified-Since도 비슷한 검증 헤더지만 초 단위 정밀도라는 한계가 있어 ETag가 더 정확하다.
프론트엔드에서는 정적 자산엔 강한 캐싱(max-age + 파일명 해시), API 응답엔 no-cache나 짧은 max-age를 적용하는 식으로 전략을 구분한다.

### Q3. WebSocket, Long Polling, Server-Sent Event(SSE)의 차이는 무엇인가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/h5bp/Front-end-Developer-Interview-Questions/blob/main/src/translations/korean/README.md)

**모범 답변:**
Long Polling은 클라이언트 요청에 서버가 새 데이터가 생길 때까지 응답을 지연시켰다가 보내는 방식으로, HTTP 요청/응답을 반복해 오버헤드가 크다.
SSE는 서버에서 클라이언트로만 단방향으로 이벤트를 지속 스트리밍하는 방식으로, 단일 HTTP 연결을 유지하며 텍스트 기반 이벤트 스트림(EventSource)을 사용한다.
WebSocket은 최초 HTTP 핸드셰이크 후 TCP 기반 양방향 풀 듀플렉스 연결로 전환되어, 채팅처럼 서버·클라이언트 모두 자유롭게 메시지를 주고받아야 할 때 적합하다.
단방향 알림이면 SSE, 양방향 실시간 상호작용이면 WebSocket을 선택하는 것이 일반적이다.

### Q4. REST API란 무엇이며 장단점은 무엇인가?

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://github.com/Esoolgnah/Frontend-Interview-Questions)

**모범 답변:**
REST(Representational State Transfer)는 자원을 URI로 표현하고 HTTP 메서드(GET/POST/PUT/PATCH/DELETE)로 자원의 상태를 조작하는 아키텍처 스타일이다.
장점은 HTTP 표준을 그대로 활용해 캐싱·상태 코드·헤더 등 기존 웹 인프라와 잘 호환되고, 무상태성 덕분에 서버 확장이 쉬우며 설계가 직관적이라는 점이다.
단점은 화면에 필요한 데이터가 여러 자원에 걸쳐 있을 때 여러 번 요청해야 하는 오버페칭/언더페칭 문제가 발생할 수 있고, 명확한 표준이 없어 팀마다 설계 방식이 달라질 수 있다는 점이다.
이런 한계 때문에 GraphQL 같은 대안이 함께 논의되곤 한다.

### Q5. HTTP란 무엇이며 어떤 특징을 가지는가?

> **importance_score**: 2/5 | **빈출**: high | **출처**: [링크](https://github.com/leegwae/getting-started/blob/main/computer-network.md)

**모범 답변:**
HTTP(HyperText Transfer Protocol)는 클라이언트와 서버가 리소스를 요청·응답 형태로 주고받는 애플리케이션 계층 프로토콜로, TCP/IP 위에서 동작한다.
가장 큰 특징은 비연결성(Connectionless)과 무상태성(Stateless)으로, 매 요청마다 새로운 연결을 맺고 이전 요청의 상태를 서버가 기억하지 않는다.
무상태성 때문에 로그인 상태 등을 유지하려면 쿠키·세션·토큰 같은 별도의 메커니즘이 필요하다.
HTTP/1.1부터는 Keep-Alive로 연결을 재사용해 매 요청마다 TCP 연결을 새로 맺는 비용을 줄였다.
