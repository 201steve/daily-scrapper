### Q1. useMemo와 useCallback의 차이점은 무엇인가요?

> **importance_score**: 4/5 | **빈출**: high | **출처**: [링크](https://velog.io/@developer-sora/%ED%94%84%EB%A1%A0%ED%8A%B8%EC%97%94%EB%93%9C-%EB%A9%B4%EC%A0%91-%EC%A7%88%EB%AC%B8-%EC%A0%95%EB%A6%AC-Part1CS-JSReact)

**모범 답변:**
useMemo는 계산 비용이 큰 "값"을 메모이제이션해 의존성 배열이 바뀌지 않는 한 재계산하지 않고 캐시된 값을 반환합니다. useCallback은 "함수" 자체를 메모이제이션해 리렌더링이 일어나도 동일한 함수 참조를 유지시켜 줍니다. 둘 다 자식 컴포넌트의 불필요한 리렌더링을 막는 최적화 용도로 사용되며, `const memoValue = useMemo(() => compute(a, b), [a, b])`, `const memoFn = useCallback(() => doSomething(a), [a])` 형태로 사용합니다.

### Q2. Context API는 무엇이고 언제 사용하나요?

> **importance_score**: 4/5 | **빈출**: high | **출처**: [링크](https://velog.io/@dnr6054/fe-interview-React)

**모범 답변:**
Context API는 props를 여러 단계로 전달하지 않고도(props drilling 없이) 컴포넌트 트리 전역에서 값을 공유할 수 있게 해주는 React 내장 기능입니다. 테마, 로그인 사용자 정보처럼 여러 컴포넌트에서 공통으로 필요한 전역 데이터를 다룰 때 주로 사용합니다. Provider로 값을 감싸고 useContext 훅으로 하위 컴포넌트에서 구독하며, 값이 자주 바뀌면 구독 중인 모든 하위 컴포넌트가 리렌더링되므로 고빈도로 변하는 상태에는 적합하지 않습니다.

### Q3. React.memo와 shouldComponentUpdate는 어떤 차이가 있으며 각각 언제 사용하나요?

> **importance_score**: 4/5 | **빈출**: high | **출처**: [링크](https://velog.io/@jim9649/%EB%A9%B4%EC%A0%91%EC%97%90%EC%84%9C-%EC%9E%90%EC%A3%BC-%EB%AC%BB%EB%8A%94-React-%EC%84%B1%EB%8A%A5-%EC%B5%9C%EC%A0%81%ED%99%94-%EA%B8%B0%EB%B2%95-%EB%B6%84%EC%84%9D%EB%B9%84%EA%B5%90)

**모범 답변:**
shouldComponentUpdate는 클래스 컴포넌트에서 props/state가 바뀔 때 호출되며 true를 반환하면 리렌더링을 수행합니다. React.memo는 함수형 컴포넌트를 감싸는 고차 컴포넌트로, 이전 props와 새 props를 얕은 비교해 같으면 리렌더링을 건너뜁니다. 두 방식은 비교 결과의 방향이 반대라는 점이 중요한데, shouldComponentUpdate는 true일 때 렌더링하지만 React.memo의 비교 함수는 false를 반환해야 렌더링이 일어납니다. props에 객체·함수가 포함되면 얕은 비교만으로 효과가 떨어지므로 useMemo/useCallback과 함께 쓰는 것이 일반적입니다.

### Q4. Redux와 Context API의 차이점은 무엇이며 각각 언제 사용해야 하나요?

> **importance_score**: 4/5 | **빈출**: high | **출처**: [링크](https://velog.io/@cada/React-Redux-vs-Context-API)

**모범 답변:**
Context API는 React 내장 기능으로 간단한 전역 상태 공유에 적합하지만, 값이 자주 바뀌는 고빈도 업데이트에는 성능이 떨어질 수 있습니다. Redux는 별도 라이브러리로 예측 가능한 단일 스토어 구조를 제공하고, redux-thunk·redux-saga·devtools 등 풍부한 미들웨어와 생태계를 갖추고 있습니다. 전역 상태가 많고 복잡한 비동기 로직이나 디버깅 도구가 필요하면 Redux(또는 Recoil 등)를, 상태 범위가 작고 단순하면 Context API를 선택하는 것이 일반적인 기준입니다.

### Q5. React 컴포넌트의 라이프사이클(마운트 → 업데이트 → 언마운트)을 설명해주세요.

> **importance_score**: 3/5 | **빈출**: high | **출처**: [링크](https://velog.io/@dnr6054/fe-interview-React)

**모범 답변:**
React 컴포넌트는 마운트(생성) → 업데이트 → 언마운트(제거)의 세 단계 라이프사이클을 가집니다. 클래스 컴포넌트 기준 마운트 시 constructor → getDerivedStateFromProps → render → componentDidMount 순으로, 업데이트 시 getDerivedStateFromProps → shouldComponentUpdate → render → componentDidUpdate 순으로 호출됩니다. componentWillUnmount는 컴포넌트가 제거되기 직전에 호출되어 타이머 해제, 이벤트 리스너 정리 등에 사용됩니다. 함수형 컴포넌트에서는 useEffect의 의존성 배열과 클린업 함수로 각 단계의 역할을 대체합니다.
